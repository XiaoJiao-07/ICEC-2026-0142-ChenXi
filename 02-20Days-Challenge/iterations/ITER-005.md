## 一、证据：三个人、三种反应、同一处缺失

`addExpense()` 记完账之后，屏幕上发生的事只有这一行（实测原文）：

```
[OK] 已记录: 17.00 [餐饮]  (耗时 40ms)
```

然后**立刻回到菜单**，没有总数、没有下一步提示、没有停顿。

三位用户在同一个位置上的反应：

| 用户 | 时刻 | 程序做了什么 | 用户做了什么 | 用户说了什么 |
|---|---|---|---|---|
| **U4** | 11-15 18:15:04 | `seq2` `add 27` 成功（44ms） | **关掉重开 3 次，最后又记一笔** | —（事后由作者说明：「他觉得没有录进去」） |
| **U5** | 11-17 19:00:52 | `seq2` `add 15` 成功（11ms） | **坐着不动，然后直接关窗** | —（记录卡第 11 项勾「坐着不动」） |
| **U6** | 11-18 22:01:07 | `seq2` `add 17` 成功（40ms） | **直接关窗口，没按 2** | **「这样就行了吗」** |

**三种反应，同一处缺失。**

- U4 的怀疑变成了**脏数据**（27 + 17 = 44 元，其中 27 是他不要的）
- U5 的怀疑变成了**沉默**（不知道下一步，坐着不动）
- U6 的怀疑变成了**一句问话**（唯一一个把不确定说出口的人）

U6 那句问话发生在 `[OK]` **之后**——**程序已经明确报成功了，用户仍然要问「这样就行了吗」**。这不是输入错误，不是操作错误，是**程序没有回答一个它本该回答的问题**。

### 1.1 为什么这一条比前几个缺陷更值得做

| 缺陷 | 用户在什么时候受损 | 造成的后果 |
|---|---|---|
| ITER-003 入口（已结案） | 还没进来 | 进不来 |
| ITER-004 日期（已关闭） | 凌晨记账 | 账落到昨天 |
| P11 报错不说人话 | 输错时 | 看不懂，再错一次 |
| **P13 记完不确认（本条）** | **做对了之后** | **重复记账 / 不信任 / 不知道下一步** |

**它是唯一一个「用户完全做对、程序却仍产生坏结果」的缺陷。** 前三者的受害者都是「操作出错的人」，这一条的受害者是**操作正确的人**。

### 1.2 与 P12（改不掉）的区别，本条不碰

| | P12 | 本条（P13） |
|---|---|---|
| 现象 | 记错了没有修改入口 | 记对了不知道该不该信 |
| 谁受害 | U4（1/6） | U4、U5、U6（3/6） |
| 修法 | 菜单里加「改刚记的那笔」 | 记完多输出两行 |

**本条只做「确认」，不做「修改」。** 一次一个变量——P12 若同时做，验证时分不清是确认语起效还是修改入口起效。

## 二、假设（可被证伪，先于改动登记）

### H1（主假设）

> **在 `[OK]` 那行下面补两行——当日笔数与合计、以及下一步可做什么——新用户记完后就不会再问「这样就行了吗」，也不会关掉重开。**

拟输出形态（尚未实施）：

```
[OK] 已记录: 17.00 [餐饮]  (耗时 40ms)
今天已记 1 笔，合计 17 元。按 2 可核对，按 1 再记一笔。
```

**预测的具体行为**：新用户看到这两行后——

1. **不会再问**「记上了吗 / 行了吗 / 这样就行了吗」这类需要人确认的话
2. **不会关掉程序重开**
3. **更可能自己按 2 去核对**（次要信号，不作硬判据）

### H2（次要假设，与 H1 可同时成立，也可单独成立）

> **光给「合计 17 元」这类事实不够，必须同时给出「下一步动作」（按 2 / 按 1）。只加事实，用户知道「记上了」但不知道「然后呢」，仍会关窗。**

依据：U5 的问题不是不信，是**不知道下一步**（坐着不动然后关窗）；U6 的问题是**不信**（问「这样就行了吗」）。两个症状不同，一行字只能治一个，所以 H1 与 H2 是分开登记的两个预测。

### 2.1 判据（现在写死，验证时不得改动）

**样本**：2 位新用户，使用同一份副本（母版 + ITER-003 + ITER-004 修复 + 本迭代改动），**首次使用前 `data/` 与 `process_logs/` 为空**。

**主判据（两条，都必须看）**：

| # | 观察项 | 通过 | 不通过 |
|---|---|---|---|
| 1 | 记完后他有没有说「行了吗 / 记上了吗 / 这样就行了吗」一类的话 | **2/2 都没有说** | 任一位说了 |
| 2 | 他有没有关掉程序重开 | **2/2 都没有重开** | 任一位重开了 |

**附加信号（只记录，不作否决）**：他有没有主动按 2；有没有再记一笔。

> 为什么「按 2」不作硬判据：按不按 2 取决于他想不想核对，与「信不信」不是一回事。把它当判据会误判——U3 按了 2 复查，是出于谨慎，不是因为程序让他安心。

### 2.2 失败条件（事先写明，不许事后改）

1. **若 2 位里仍有 1 位问「这样就行了吗」→ H1 不成立（至少部分不成立）。**
   含义：缺的不是「总数」，是他根本不确定这个程序在做什么。下一步应转向形态与流程引导，而不是再加一行字。
2. **若 2 位都没问，但也没按 2、直接关窗 → H1 成立，H2 未获支持。**
   含义：他不再怀疑账记上了，但依然不想再打开。**这不算失败**，只说明确认语解决的是「信任」，不是「留存」。
3. **若没有观测记录（记录卡没填、没保存）→ 记为「未观测」，不计通过也不计失败。**
   U6 那次就差点变成这种结果，教训是「证据没落地就等于没有」。

### 2.3 预先承认的局限（写在这里，防止事后拿它当意外）

1. **本迭代不改善留存。** 6 位用户里 0 位愿意继续用，理由集中在「太麻烦」「不如用手机」——那是需求与形态问题，不是确认语能解决的。**不能拿「留存仍为 0」来否定 H1，也不能拿 H1 成立来宣称留存有救。**
2. **样本只有 2 位，结论强度有限。** 与 ITER-003 同规格，不写「已解决」，只写「2 位新用户下成立」。
3. **「不问」不等于「信了」。** 判据测的是外显行为，不是内心状态。若他沉默着关窗，只能说「他没有表达怀疑」，不能说「他放心了」。
4. **改动会触及所有成功提示。** `addExpense` 与 `batchAdd` 两处都要动；只改交互式菜单会让 CLI 路径与交互路径说法不一致。

## 三、改了什么

### 3.1 具体改动（`main.js`，共 3 处，+11 行）

**(1) 新增辅助函数**（`// ==================== 核心功能 ====================` 之后）：

```js
// ITER-005（2026-11-19）：记完后回答「这样就行了吗」
// 依据：U6 在 [OK] 之后仍问「这样就行了吗」；U4 不信重开 3 次；U5 坐着不动
// 只加输出，不改逻辑：data 已由 loadData() 取得，此处零额外 IO
function todayLine(data, today) {

  const sum = list.reduce(function (s, e) { return s + e.amount; }, 0);

}
```

**(2) `addExpense()` 成功分支**，在 `[OK]` 那行之后新增一行：

```js

```

**(3) `batchAdd()` 成功分支**，在 `批量记账完成` 那行之后新增一行：

```js

```

> 批量那处不带「按 2 / 按 1」：批量本身已经报了 `成功 4/4 笔`，用户此刻是在命令行里跑，不需要菜单指引。**交互路径给动作，CLI 路径给事实。**

### 4.3 一条机制性观察：确认语的「独占时间」接近于零

新增行印出后，**紧接着就是 12 行菜单 + 「请输入序号:」的重印**，中间没有任何停顿。人工输入一次「序号 + 回车」通常要 1–2 秒——也就是说，那两行确认信息在屏幕上的独占时间**接近于零**，下一屏立刻压上来。

这可能解释「加了字仍要问」：确认语在视觉上被菜单冲掉，等于把用户送回「又回到起点了」的状态。

**但这是观察，不是结论**，也不构成对 H1 的第二次解释权——H1 是「补两行文字就够了」，实际是「补了两行、但没有让它停住」。

### 4.5 ITER-005 专项三格：这是第一次填全，也第一次抓到「手指停了」

`用户测试-08/09` 两版记录卡都加了 G/H/I 三格，只有 U8 填全：

**H 格是本迭代最关键的一条新证据**：手指停了，说明那行字**被看到、被处理过**。停完之后他没有按 2 核对——这一点成立；但「按了 0 退出」这一点，**在 13:19 归档时被进程证据推翻**，见 4.5b。

### 4.5b 一条被进程证据推翻的记录：U8 没有按 0

2026-11-22 13:19 归档 `用户测试-09` 时 `mv` 报 `Device or resource busy`。查得：

| 证据 | 内容 |
|---|---|
| `cmd.exe` PID 120428 | `cmd.exe /c ""…\用户测试-09\①双击我记账.bat""`，**仍在运行** |
| `node.exe` PID 116688 | `…\用户测试-09\runtime\node.exe`，**启动时间 13:05:56**，与遥测 `seq1 startup 13:05:56.600` 同一秒 |

`app.js:107` 是 `else if (choice === '0') { … rl.close(); process.exit(0); }`——**按 0 必然退出进程**。该进程活到 13:19，且遥测无第二条 `startup`（排除退出后重开），结论只能是：**13:06:08 之后的 13 分钟里，`0` 没有被按下，他就起身走了，程序停在菜单上。**

边界三条：①「手指停了」这条观察仍成立，它证明那行字被读到，只是停完按的不是 0；②「窗口开着」本身不能证明 node 没退（bat 末尾有 `pause`），**真正的证据是进程存活时间**，两个证据不能混用；③他起身的精确时刻未知，只能说「13:06:08 之后、13:19 之前的某一点」。

**方法学收获**：记录卡把 `0` 预设成唯一出口（G 格选项直接写「完全没看，直接按 0」），填卡的人就顺着写了「按 0」——**模板自己生产了一个不存在的动作**。

## 五、结论（2/2 完成，按预注册规则下结论）

### 5.1 H1：**不成立**

> H1：在 `[OK]` 下面补「当日笔数与合计 + 下一步可做」两行，新用户记完就不会再问「这样就行了吗」，也不会关掉重开。

| 半句 | 实测 | 判定 |
|---|---|---|
| 「不会再问」 | **2/2 都问了**（U7 一字不差、U8 换了个说法） | **不成立** |
| 「不会关掉重开」 | 2/2 都是 1 次启动 | 成立（这一半有效） |

**H1 兑现了一半，而失掉的那一半正是它的主要目的。** 按 2.2 的判断原则，**不拆成「部分成立」来记**——主判据是「不问」，0/2 就是不成立。

### 5.2 H2：**未获支持（2/2）**

> H2：光给「合计 17 元」这类事实不够，必须同时给出「下一步动作」（按 2 / 按 1），否则仍会关窗。

两位拿到的都是**事实 + 动作**，结果是：

- U7 → **坐着不动**
- U8 → **什么都没按，起身走了**（手指在那行字上停过半秒，然后既没按 2、也没按 0；程序停在菜单上开着，13:19 才被发现并结束——见 4.5b）

**两个人的附加信号都是「没有按 2」；而且 0/2 人按过 0。** 那行字给了两个动作，两位一个都没用。H2 的前提（「给了动作就会动」）两次都没有出现。

但必须写清：**「动作」和「事实」是同一行印出来的，无法分离**，所以严格说 H2 只是「未获支持」，不是「被证伪」——要证伪它，得让一组用户只看到动作、另一组只看到事实，**本轮没有做，也不打算补做**（样本只有 8 位，再做分组会两头都不够）。

### 5.3 那到底缺什么：一条由证据推出的读法（仍不是假设）

把四件事放在一起：

1. 合计行回答了「记上了没有」——2/2 仍然问「这样行了吗」；
2. 「按 2 / 按 1」告诉了他能做什么——2/2 都没按 2，**也都连 0 都没按**；
3. **U8 的手指在那行字上停过半秒**——他读到了，不是没读到；
4. 屏幕的**终态始终是「请输入序号:」**，唯一的出口是 `0`，而 `0` 没有任何一行解释。

**他缺的不是「信息」，是「结束」。** 程序从进入那一刻起，永远不会告诉用户「这一次完了，你可以走了」。U7 留在原地等，U8 干脆走人、把程序留在菜单上——**两种形态，同一个缺口**。

**这条读法只能算「对现象的解释」，还不是假设**——按本项目规矩，它必须在**下一轮改动之前**先登记成可证伪的形式（预测什么行为、什么算推翻），才能进 ITER-006。**本轮不做任何代码改动。**

### 5.4 这次迭代算不算失败

**算一次完整的迭代，不算无效工作。**

- 假设先于代码（`24d63ff`，11-18 22:28），改动在 11-19 22:16，时序可查；
- 判据、失败条件、局限全部写死在改动之前，事后一条没改；
- 2 位用户、2/2 撞失败条件，**结论是硬的不成立，不是「样本不足」**；
- 结果推翻了主假设，**同时给出了一条更强的线索（缺「结束态」）**；
- 第一次拿到了两类**不依赖口述**的物理证据：U8 的手指停顿（肉眼观察）、U8 的程序进程从 13:05:56 一直存活到 13:19（可复现的进程证据，见 4.5b）。

**按本项目的口径：被推翻的迭代仍是完整迭代，未验证的迭代才是扣分项。**

## 六、下一步：**不做了**（2026-11-22 决定，写在这里防止事后补故事）

「缺一个结束态」这条线索指向一个显而易见的改法：确认语之后加一次停顿（例如「按回车继续」），或者给 `0` 加一行「退出」的解释，让屏幕出现一个明确的「这次完了」的状态。

**本迭代不做，也不在封仓前开 ITER-006。** 理由三条，按重要性排：

1. **封仓 11-24，一个迭代要走完「假设登记 → 改动 → 第 9 位用户验证」三步。** 如果只登记、改了、没等到人验证，产出的就是**未验证的迭代**——按本项目自己的口径，那才是扣分项，比「没做」更差。
2. **样本已经用掉 8 位。** 第 9 位要么没有，要么只能由作者本人充当——**本人自测不能算「新用户」证据**，写进报告只能算自测，价值低于一次干净的不做。
3. **一次一个变量。** ITER-005 刚证明「加一行字」不解决这个问题，紧接着再叠一个「加一次停顿」，即便下一位用户不问，也分不清是停顿起效还是他本来就懒得问。

### 6.1 若将来要做，会这样登记（**本轮未登记、未实施，仅存档思路**）

- **假设**：在 `[OK]` 之后加一次强制停顿（需按回车才回菜单），并把 `0` 解释为「退出」，新用户记完后的**第一动作不再是「问人」或「发呆」**。
- **判据**：2 位新用户，**2/2 在停顿处没有任何询问、且 2/2 能自己说出下一步**（说出「按回车继续」或「0 是退出」即可，不要求按 2）。
- **失败条件**：任一位在停顿处问「这要干嘛 / 怎么回去」，或任一位按键前停顿超过 5 秒仍不动 → 假设不成立。
- **预先承认的局限**：停顿会增加每一次记账的摩擦；若用户抱怨「多按一次很烦」，那就是用「明确」换了「快」，是取舍不是纯改进。

**这段是思路，不是承诺。** 写下来的目的只有一个：**若有人问「你都知道缺结束了，为什么不做」，答案在这里，而且是在做之前写的。**

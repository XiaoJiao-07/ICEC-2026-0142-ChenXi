## 一、证据：三个人、三种反应、同一处缺失

`addExpense()` 记完账之后，屏幕上发生的事只有这一行（实测原文）：

```
[OK] 已记录: 17.00 [餐饮]  (耗时 40ms)
```

然后**立刻回到菜单**，没有总数、没有下一步提示、没有停顿。

三位用户在同一个位置上的反应：

| 用户 | 时刻 | 程序做了什么 | 用户做了什么 | 用户说了什么 |
|---|---|---|---|---|
| **U4** | 11-15 18:15:04 | `seq2` `add 27` 成功（44ms） | **关掉重开 3 次，最后又记一笔** | —（事后由作者说明：「他觉得没有录进去」） |
| **U5** | 11-17 19:00:52 | `seq2` `add 15` 成功（11ms） | **坐着不动，然后直接关窗** | —（记录卡第 11 项勾「坐着不动」） |
| **U6** | 11-18 22:01:07 | `seq2` `add 17` 成功（40ms） | **直接关窗口，没按 2** | **「这样就行了吗」** |

**三种反应，同一处缺失。**

- U4 的怀疑变成了**脏数据**（27 + 17 = 44 元，其中 27 是他不要的）
- U5 的怀疑变成了**沉默**（不知道下一步，坐着不动）
- U6 的怀疑变成了**一句问话**（唯一一个把不确定说出口的人）

U6 那句问话发生在 `[OK]` **之后**——**程序已经明确报成功了，用户仍然要问「这样就行了吗」**。这不是输入错误，不是操作错误，是**程序没有回答一个它本该回答的问题**。

### 1.1 为什么这一条比前几个缺陷更值得做

| 缺陷 | 用户在什么时候受损 | 造成的后果 |
|---|---|---|
| ITER-003 入口（已结案） | 还没进来 | 进不来 |
| ITER-004 日期（已关闭） | 凌晨记账 | 账落到昨天 |
| P11 报错不说人话 | 输错时 | 看不懂，再错一次 |
| **P13 记完不确认（本条）** | **做对了之后** | **重复记账 / 不信任 / 不知道下一步** |

**它是唯一一个「用户完全做对、程序却仍产生坏结果」的缺陷。** 前三者的受害者都是「操作出错的人」，这一条的受害者是**操作正确的人**。

### 1.2 与 P12（改不掉）的区别，本条不碰

| | P12 | 本条（P13） |
|---|---|---|
| 现象 | 记错了没有修改入口 | 记对了不知道该不该信 |
| 谁受害 | U4（1/6） | U4、U5、U6（3/6） |
| 修法 | 菜单里加「改刚记的那笔」 | 记完多输出两行 |

**本条只做「确认」，不做「修改」。** 一次一个变量——P12 若同时做，验证时分不清是确认语起效还是修改入口起效。

## 二、假设（可被证伪，先于改动登记）

### H1（主假设）

> **在 `[OK]` 那行下面补两行——当日笔数与合计、以及下一步可做什么——新用户记完后就不会再问「这样就行了吗」，也不会关掉重开。**

拟输出形态（尚未实施）：

```
[OK] 已记录: 17.00 [餐饮]  (耗时 40ms)
今天已记 1 笔，合计 17 元。按 2 可核对，按 1 再记一笔。
```

**预测的具体行为**：新用户看到这两行后——

1. **不会再问**「记上了吗 / 行了吗 / 这样就行了吗」这类需要人确认的话
2. **不会关掉程序重开**
3. **更可能自己按 2 去核对**（次要信号，不作硬判据）

### H2（次要假设，与 H1 可同时成立，也可单独成立）

> **光给「合计 17 元」这类事实不够，必须同时给出「下一步动作」（按 2 / 按 1）。只加事实，用户知道「记上了」但不知道「然后呢」，仍会关窗。**

依据：U5 的问题不是不信，是**不知道下一步**（坐着不动然后关窗）；U6 的问题是**不信**（问「这样就行了吗」）。两个症状不同，一行字只能治一个，所以 H1 与 H2 是分开登记的两个预测。

### 2.1 判据（现在写死，验证时不得改动）

**样本**：2 位新用户，使用同一份副本（母版 + ITER-003 + ITER-004 修复 + 本迭代改动），**首次使用前 `data/` 与 `process_logs/` 为空**。

**主判据（两条，都必须看）**：

| # | 观察项 | 通过 | 不通过 |
|---|---|---|---|
| 1 | 记完后他有没有说「行了吗 / 记上了吗 / 这样就行了吗」一类的话 | **2/2 都没有说** | 任一位说了 |
| 2 | 他有没有关掉程序重开 | **2/2 都没有重开** | 任一位重开了 |

**附加信号（只记录，不作否决）**：他有没有主动按 2；有没有再记一笔。

> 为什么「按 2」不作硬判据：按不按 2 取决于他想不想核对，与「信不信」不是一回事。把它当判据会误判——U3 按了 2 复查，是出于谨慎，不是因为程序让他安心。

### 2.2 失败条件（事先写明，不许事后改）

1. **若 2 位里仍有 1 位问「这样就行了吗」→ H1 不成立（至少部分不成立）。**
   含义：缺的不是「总数」，是他根本不确定这个程序在做什么。下一步应转向形态与流程引导，而不是再加一行字。
2. **若 2 位都没问，但也没按 2、直接关窗 → H1 成立，H2 未获支持。**
   含义：他不再怀疑账记上了，但依然不想再打开。**这不算失败**，只说明确认语解决的是「信任」，不是「留存」。
3. **若没有观测记录（记录卡没填、没保存）→ 记为「未观测」，不计通过也不计失败。**
   U6 那次就差点变成这种结果，教训是「证据没落地就等于没有」。

### 2.3 预先承认的局限（写在这里，防止事后拿它当意外）

1. **本迭代不改善留存。** 6 位用户里 0 位愿意继续用，理由集中在「太麻烦」「不如用手机」——那是需求与形态问题，不是确认语能解决的。**不能拿「留存仍为 0」来否定 H1，也不能拿 H1 成立来宣称留存有救。**
2. **样本只有 2 位，结论强度有限。** 与 ITER-003 同规格，不写「已解决」，只写「2 位新用户下成立」。
3. **「不问」不等于「信了」。** 判据测的是外显行为，不是内心状态。若他沉默着关窗，只能说「他没有表达怀疑」，不能说「他放心了」。
4. **改动会触及所有成功提示。** `addExpense` 与 `batchAdd` 两处都要动；只改交互式菜单会让 CLI 路径与交互路径说法不一致。

## 三、改了什么

**实施时间：2026-11-19 22:16**（假设登记于 22:28 之前一晚的 `24d63ff`，本节可证改动在假设之后）。

### 3.1 具体改动（`main.js`，共 3 处，+11 行）

**(1) 新增辅助函数**（`// ==================== 核心功能 ====================` 之后）：

```js
// ITER-005（2026-11-19）：记完后回答「这样就行了吗」
// 依据：U6 在 [OK] 之后仍问「这样就行了吗」；U4 不信重开 3 次；U5 坐着不动
// 只加输出，不改逻辑：data 已由 loadData() 取得，此处零额外 IO
function todayLine(data, today) {
  const list = data.expenses.filter(function (e) { return e.date === today; });
  const sum = list.reduce(function (s, e) { return s + e.amount; }, 0);
  return '今天已记 ' + list.length + ' 笔，合计 ' + sum.toFixed(2) + ' 元。';
}
```

**(2) `addExpense()` 成功分支**，在 `[OK]` 那行之后新增一行：

```js
console.log(`${todayLine(data, today)}按 2 可核对，按 1 再记一笔。`);
```

**(3) `batchAdd()` 成功分支**，在 `批量记账完成` 那行之后新增一行：

```js
console.log(todayLine(data, today));
```

> 批量那处不带「按 2 / 按 1」：批量本身已经报了 `成功 4/4 笔`，用户此刻是在命令行里跑，不需要菜单指引。**交互路径给动作，CLI 路径给事实。**

### 3.2 没有改的东西（同样重要）

| 项 | 为什么不动 |
|---|---|
| 版本号（仍是 `v2.4`） | 只是输出文案，不是功能版本；改版本号会让 `用户测试-07`（U6 用过）与 `08` 多出一个无意义的差异，验证时多一个变量 |
| `(耗时 40ms)` 那一段 | 用户看不懂毫秒，它确实像调试信息（可单独立项 P15），但**一次只改一个变量**，本轮不动 |
| 数据结构、`date` 字段、`localDate()` | ITER-004 刚修完，不碰 |
| 遥测格式 | `seq` / `prev_hash` / `action` / `details` 全部未变，链的连续性不受影响 |
| 失败路径（`catch` 分支） | **故意不加合计**：记失败时给出「今天已记 N 笔」会让用户误以为记上了 |

### 3.4 一条必须写明的自测局限

**交互式菜单在管道输入下跑不通**：`printf '1\n17\n1\n\n0\n' | node app.js menu` 会卡在「金额（元）:」，改重定向到文件同样卡住（readline + 中文提示 + 非交互 stdin）。

所以本轮自测走的是**函数级调用**（`require('./main.js')` 后直接调 `addExpense` / `batchAdd`），**不是菜单级端到端**。

这不影响结论，理由有两条：

1. `app.js` 的 `choice === '1'` 分支只有三个 `await ask` 加一行 `addExpense(...)`，中间**没有任何额外逻辑**；
2. 菜单这条路径已被 U4/U5/U6 三次真人使用验证过（他们都从菜单进入了记账流程）。

但仍要写清楚：**我测的是被调用的函数，不是用户点的那条路。** 真机验证只能靠第 7 位用户。

## 四、验证结果

（判据要求 2 位新用户，目前完成 **1 位**。**未达 2 位，「已修复」三个字不写。**）

### 4.1 第 1 位用户（U7，2026-11-21 11:29–11:30:42，`用户测试-08`）

| 判据 | 标准 | 实测 | 判定 |
|---|---|---|---|
| 1 | 记完后没说「行了吗」类的话 | **说了：「这样就行了吗」** | **不通过**（时序待作者确认，见 4.2） |
| 2 | 没有关掉重开 | 遥测 **仅 1 行 `startup`**，账本 1 笔 | **通过** |

**屏幕实录（截图可证）**：新增行确实印出来了，位置在 `[OK]` 正下方——

```
[OK] 已记录: 13.00 [餐饮]  (耗时 10ms)
今天已记 1 笔，合计 13.00 元。按 2 可核对，按 1 再记一笔。
```

**所以这不是「改动没生效」，是「改动了、仍没答到他的问题」。** 两种情况性质完全不同，必须分开写。

按 2.2 第 1 条预注册的失败条件（「若 2 位里仍有 1 位问 → H1 不成立（至少部分不成立）」），**第 1 位就撞上了**。按规则，H1 此时已可判为「不成立（部分）」，不必等第 2 位才下结论；第 2 位的作用变成测「是否 2/2」并给 H2 提供样本。

### 4.2 一处必须先确认的时序（否则这句话不能当「确认语无效」的证据）

| 时序 | 含义 | 对 H1 的判定 |
|---|---|---|
| **A. 看到合计行之后问的** | 字印出来了，他仍然要问 → 这行字没答到他的问题 | H1 **不成立** |
| **B. 在「备注（直接回车跳过）:」按回车之前问的** | 结果还没出来，程序什么都还没说 | 这句话测的不是确认语，H1 **未获验证** |

**在作者答复前，本节按「不通过（待定时确认）」记录，不擅自选定。**

### 4.3 一条机制性观察：确认语的「独占时间」接近于零

新增行印出后，**紧接着就是 12 行菜单 + 「请输入序号:」的重印**，中间没有任何停顿。人工输入一次「序号 + 回车」通常 1–2 秒——也就是说，那两行确认信息在屏幕上的独占时间**接近于零**，下一屏立刻压上来。

这可能解释「加了字仍要问」：确认语在视觉上被菜单冲掉，等于把用户送回「又回到起点了」的状态。

**但这是观察，不是结论**，也不构成对 H1 的第二次解释权——H1 是「补两行文字就够了」，实际是「补了两行、但没有让它停住」。若要做下去，那是 ITER-005b 的范围（例如确认语后加一次「按回车继续」的停顿），**本轮不做，一次一个变量**。

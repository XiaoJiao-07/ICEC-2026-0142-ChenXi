# ITER-004 桩钟实验 · 复现步骤与原始输出

**目的**：在不改系统时间、不依赖真人早起的前提下，端到端验证「本地 00:00–07:59 记账落库到前一天」这一缺陷，以及修复是否生效。

**时间**：2026-11-16 18:35–18:40（作者 11-16 早上忘记记录，原计划的"明早真实一笔"未发生，故补做本实验）

---

## 一、方法

`stub_clock.js` 只做一件事：把进程内的无参 `new Date()` 和 `Date.now()` 固定到 `STUB_ISO` 指定的时刻。**不改系统时钟、不改文件时间戳。**

用 `node -r` 在加载被测算程序之前预加载它，然后照常跑 `app.js batch`，再读回写出的 `data/expenses.json`。

**A/B 对照**：同一桩钟、同一命令，分别喂旧代码与新代码。

- 旧代码：`git show 299da6e:02-20Days-Challenge/课题04-校园生活费记账工具/main.js`
- 新代码：`789b535` 之后的 `main.js`

## 二、复现命令

```bash
# 1. 准备隔离环境（不要用真实账本目录）
T="$TEMP/iter004_ab"
mkdir -p "$T/data" "$T/process_logs"
cp app.js main.js stub_clock.js "$T/"
cp -r src "$T/"

# 2. 用桩钟跑一次真实记账
cd "$T"
STUB_ISO='2026-11-16T00:30:00+08:00' node -r ./stub_clock.js app.js batch "5,餐饮,受控实验"

# 3. 读回落库日期
node -e "console.log(require('./data/expenses.json').expenses.map(e=>e.date))"
```

换代码版本时：把 `main.js` 换成另一版，删掉 `data/expenses.json` 与 `process_logs/*.log`，重跑第 2 步。

## 五、这个实验证明不了什么（必须一起写）

1. **桩钟不是系统时间**：证明的是"程序取哪个日期"，不是"在真实早晨运行会怎样"。
2. **真实场景仍未验证**：本地 00:00–07:59 的真实运行，至今没有被观测过一次。
3. 因此最终报告只能写「受控实验通过、真实场景未验证」，不能写「已修复并经真实场景确认」。

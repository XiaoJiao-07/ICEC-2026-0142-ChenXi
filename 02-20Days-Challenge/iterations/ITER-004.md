## 一、缺陷本身

`main.js` 取"今天"用的是：

```js
const today = new Date().toISOString().split('T')[0];
```

`toISOString()` 返回的是 **UTC 时间**。作者在中国（UTC+8），本地时间要减 8 小时才是 UTC。因此：

**本地 00:00–07:59 记账 → UTC 还是前一天 → 账落到昨天。**

### 1.1 可复现的证明（不改系统时间、不依赖运气）

```
$ node -e "…用四个时刻验证…"
早上 00:30 记账 | 本地 2026-11-15 00:30 | 落库日期 2026-11-14 | 错前一天
早上 07:59 记账 | 本地 2026-11-15 07:59 | 落库日期 2026-11-14 | 错前一天
早上 08:01 记账 | 本地 2026-11-15 08:01 | 落库日期 2026-11-15 | 正确
深夜 23:50 记账 | 本地 2026-11-15 23:50 | 落库日期 2026-11-15 | 正确
```

**错误窗口精确为本地 00:00:00–07:59:59，每天 8 小时，占一天的三分之一。**

### 1.2 为什么这个缺陷特别难被"用"发现

| 谁 | 会不会撞上 | 为什么 |
|---|---|---|
| 作者自测 | 不会 | 我都是晚上 19:00–23:00 记账 |
| U1/U2/U3 | 不会 | 三次测试都在 21:40–22:30 |
| **真实用户** | **会，而且是最常见的那一笔** | **早餐。**一个人一天里最可能"当场记一笔"的时刻，就是早上买完早饭那两分钟 |

**这是"自测永远测不出来"的第二类问题**（第一类是 ITER-003 的入口：程序员不会双击 `node.exe`）。两者的共同点是：**开发者的行为习惯，恰好绕开了缺陷的触发条件。**

### 1.3 与 P7 的区别（不能混为一谈）

| | P7（U3 撞上） | 本缺陷（P10） |
|---|---|---|
| 现象 | 用户想记"昨天"，落库成今天 | 用户想记"今天"，落库成昨天 |
| 原因 | 功能设计：`1. 记一笔` 只能写当天，改日期要走 `b`，用户不知道 | 代码缺陷：取的"当天"是 UTC 的当天 |
| 触发条件 | 任何时刻，只要记的不是今天 | 只在本地 00:00–07:59 |
| 用户能否察觉 | 不能 | 不能（列表里日期看着"就是昨天那笔"，反而更自洽） |

**两个方向相反的日期错误，都会让账本悄悄变错，而用户以为自己记对了。** 这是同一类伤害的两个面。

## 二、假设（可被证伪）

### H1（根因是时区换算）

> 把 10 处 `toISOString().split('T')[0]` 全部换成本地日期格式化函数后，本地 00:00–07:59 的记账应落到当天，其余时刻行为不变。

**若成立**：第四节四时刻测试中，00:30 与 07:59 两行变成"正确"，08:01 与 23:50 仍为"正确"，且历史 28 条数据一条不动。

### H2（存在更深的第二处）

> 除了取日期，`created_at`（显示用）与"最近 N 天"的截断逻辑也各自独立取时间，可能存在第二处不一致。

**若成立**：改完日期字段后，`list 7` 的起止边界、`周报`、`月报` 出现跨日错位（例如 11-09 的记录在第 7 天被提前剔除）。

### 判据（数据前写定）

| 检查项 | 通过标准 |
|---|---|
| 四时刻测试 | 00:30 / 07:59 均落当天；08:01 / 23:50 不变 |
| 历史数据完整性 | `data/expenses.json` 28 条，`id`、`date`、`amount` 逐条不变 |
| 列表边界 | `list 7` 在 11-15 应包含 11-09 及之后，不吞不多 |
| 真实场景 | **明早 08:00 前记一笔早餐，列表里日期必须是当天**（唯一需要真人的一步） |

## 三、改了什么

**改动时间：2026-11-15 18:12–18:20。** 假设先提交（`299da6e`，18:10），改动在其后。

### 3.1 新增两个本地日期函数（`main.js`，基础函数区）

```js
// 2026-11-15 ITER-004：一律用「本地日期」，不用 toISOString()。
// toISOString() 返回 UTC，本地 00:00–07:59 会被算成前一天——而这段时间正好是"早餐那一笔"。
function pad2(n) { return String(n).padStart(2, '0'); }
function localDate(d = new Date()) { return `${d.getFullYear()}-${pad2(d.getMonth() + 1)}-${pad2(d.getDate())}`; }
function localMonth(d = new Date()) { return `${d.getFullYear()}-${pad2(d.getMonth() + 1)}`; }
```

### 3.2 十处替换（一次性全部换掉，不留半改状态）

| 位置 | 原写法 | 新写法 |
|---|---|---|
| `addExpense` / `batchAdd` / `checkAnomaly`（3 处） | `new Date().toISOString().split('T')[0]` | `localDate()` |
| `listExpenses` / `weeklyReport` / `trendChart` / `checkAnomaly` 的截断（4 处） | `cutoff.toISOString().split('T')[0]` | `localDate(cutoff)` |
| `dailySummary` 默认日期 | 同上 | `localDate()` |
| `checkBudget` 月区间（2 行） | `now.toISOString().slice(0,7)` | `localMonth(now)` |
| `monthlyReport` 默认月份 | `new Date().toISOString().slice(0,7)` | `localMonth()` |
| `backupData` 备份文件名 | `…toISOString().split('T')[0]…` | `localDate()` |

改完 `grep toISOString main.js` 仅剩两行**注释**，无任何调用。

**为什么全换而不是只改 `addExpense`**：只改写入、不改截断，会出现"新数据按本地日期存、旧查询按 UTC 日期筛"的错位——第 7 天边界正好差一天。这种半改比不改更难查。

### 3.3 为可测试性加的一行

`module.exports` 里补 `localDate, localMonth`。**理由**：这两个函数必须能被固定时刻驱动测试，否则只能等明天早上，等于把验证交给运气。这不是功能改动。

### 3.4 自测（改完当天，不算真实场景验证）

**A. 固定时刻对照（同一时刻，两种写法）**

```
固定时刻 2026-11-15 00:30 (UTC+8)
  旧写法 toISOString: 2026-11-14   ← 落库到昨天
  新写法 localDate   : 2026-11-15   ← 正确
```

**B. 回归（功能未坏）**

| 命令 | 结果 |
|---|---|
| `node --check main.js` | 语法通过 |
| `summary` | `2026-11-15 … 总计 23.00 (4笔)` |
| `list 7` | 回到 11-09，**合计 235.00 (28笔)**，边界不多不少 |
| `monthly` | 11-09 至 11-15 七天逐日列出，无缺日 |

**C. 历史数据零变动**：28 条、合计 235 元，`id`/`date`/`amount` 全部未动（本次只改代码，不迁移数据）。

### 3.5 一条必须写明的自测局限

我本想用 `TZ` 环境变量把同一时刻切换到别的时区来交叉验证，但**这台机器上的 Node 不响应 `TZ`**（设 `Etc/GMT+12` 与 `Pacific/Kiritimati` 结果完全相同）。所以：

**"早间窗口"这一条，代码层只能靠 A 的固定时刻对照证明，运行层必须等明早的真实一笔。** 不把 A 当成"已验证"。

### 3.6 未采用的做法

| 方案 | 为什么不采用 |
|---|---|
| 只改 `addExpense` 一处 | 会造成"写入按本地、查询按 UTC"的错位，第 7 天边界差一天（见 3.2） |
| 把系统时区改成 UTC | 治标不治本：手机用户在任何时区都会遇到同一问题，而代码是给别人用的 |
| 数据迁移（把已有的错日期往前挪一天） | **不能做**。历史记录里既有"真记在昨天"的，也有"被 UTC 算错的"，无法区分；改了就毁了真实数据 |

## 二、我的假设（可被证伪）

### H1（语言为首因）

> 界面全英文，是用户在第一步就放弃的主要原因。

**若成立**，中文化之后，一位**全程不给任何口头提示**的新用户，应当能自行看懂菜单、选到"1. 记一笔"、并完成一笔记账。

### H2（步骤为首因）

> 真正的障碍不是语言，而是"记一笔账必须先选一次菜单项，再输金额、再选类别"这套四层结构。

**若成立**，中文化之后，新用户仍会在同一处停手，或仍抱怨"还要点一下""太麻烦"。

### 裁决方式（次日执行）

找 1–2 位**未接触过本项目**的新用户，只说一句"你试着记一笔昨天午饭"，**之后全程不说话、不指、不替他按**，记录三件事：

| 观察项 | 记录方式 |
|---|---|
| 是否自行按 `1` | 有 / 无；用时多少秒 |
| 是否完成记账 | 账本是否新增 1 条 |
| 说了什么 | 原话逐字 |

**判定**：

- 自主完成 → **H1 得到支持**，P4（英文）为首因，ITER-003（一行式输入）可降级
- 仍需提示或仍说"麻烦" → **H2 得到支持**，P4 只是表层，ITER-003 升为最高优先

### 这条假设可能失败的地方（预先写明）

1. 中文化后，用户输入中文数字"一"而非"1"，反而产生新的无效输入 → 需要记录，不能当作 H1 成立
2. 用户根本不看菜单，直接输金额（U1 首次输入 `23` 即属此类）→ 说明 H2 从一开始就是主因
3. 命令行窗口本身对非技术用户仍是障碍（与语言无关）→ 属于第三类解释，本轮不测

## 三、改了什么

### 3.1 改动范围（仅交互菜单，不含 CLI）

| 位置 | 改前 | 改后 |

| 9 个菜单项 | `1. Add expense … 0. Exit` | `1. 记一笔 … 0. 退出` |
| 主提示 | `Enter number: ` | `请输入序号: ` |
| 金额 | `Amount (yuan): ` | `金额（元）: ` |
| 类别表 | `1-Food 2-Transport … 7-Other` | `1-餐饮 2-交通 3-购物 4-娱乐 5-学习 6-医疗 7-其他` |

| 退出 | `Bye!` | `再见！` |

**另外两处刻意没改**：

1. **CLI 帮助（`node app.js help`）保持英文**——已有脚本、日志、截图都按英文参数运行，改它不影响用户测试，却会增加不一致的风险。**这是取舍，不是遗漏。**
2. **类别在数据里本来就是中文**（`餐饮/交通/…`），只是界面用英文标签映射。这次只改标签，不动存储格式，历史数据零影响。

### 3.4 未采用的做法

| 方案 | 为什么不采用 |
|---|---|
| 中英双语并列（`1. 记一笔 / Add expense`） | 屏幕更挤，且两位用户的问题都不是"缺英文"，是"只有英文" |
| 只改类别表，不改菜单 | U2 说的是"进去之后全是英文"，指整屏，不是单指类别 |
| 顺手把 CLI 也中文化 | 会打乱既有日志与截图的一致性，收益为零，风险不小 |

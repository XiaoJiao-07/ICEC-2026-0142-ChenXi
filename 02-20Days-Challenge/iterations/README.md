# iterations/ — 数据驱动的迭代记录

本目录对应考核第二阶段（Project 04）20 分项：**`3+ data-driven Git commit iterations`**。
关键词是 **data-driven**：每一次迭代的依据必须来自 `process_logs/` 里的真实日志，不是「我想加个功能」。

---

## 命名与数量

- `ITER-001.md`、`ITER-002.md`、`ITER-003.md`（至少 3 个）
- 一个迭代 = 一次完整的「发现 → 推断 → 修改 → 验证」闭环，**跨两天完成**（第一天改，第二天验证）

## 每个文件必须有四段

### 1. 日志证据（原文，不是转述）

从 `process_logs/telemetry_YYYY-MM-DD.log` 里粘**相关的那几行原文**，并给出定位：

```
2026-11-12T10:41:07.318+08:00 | seq=37 | action=export_csv | elapsed_ms=41 | ...
2026-11-12T10:41:12.902+08:00 | seq=38 | action=export_csv | elapsed_ms=44 | ...
```

要写清：**这是从哪天哪个文件的第几行来的**。评委要能自己 grep 到。

### 2. 我的假设（一句话，可被证伪）

好例子：「`export_csv` 每次都全量重写整个文件，所以耗时随记录条数线性增长。」
坏例子：「导出有点慢，我优化一下。」——不可证伪，等于没假设。

### 3. 改了什么（指向具体 commit）

- commit：`abc1234`
- 改了哪个函数、改了几行
- `git diff` 的关键片段
- 为什么选这个改法，放弃了什么别的方案

### 4. 次日验证结果（必须第二天填，不能当天编）

- 改完后第二天的日志里，同一个 action 的 `elapsed_ms` 变成多少
- **如果没变好 / 变差了，如实写**。改了没效果是正常结果，写出来比假装成功可信
- 附带一句「下一步」

---

## 为什么这块能拿分

| 常见做法 | 本目录要求 |
|---|---|
| 「新增批量记账功能」 | 「日志显示 10-12 有 6 次连续单笔 `add`，间隔均 < 8s → 假设用户在手敲 → 加批量入口 → 次日 `add_batch` 出现 3 次」 |
| 功能清单 | 证据链 |
| 一次提交说三个功能 | 一次提交解决一个被日志证明的问题 |

评委面试第 1 维会直接问「commit diff 里这个改动为什么这么写」——这个目录就是答案。

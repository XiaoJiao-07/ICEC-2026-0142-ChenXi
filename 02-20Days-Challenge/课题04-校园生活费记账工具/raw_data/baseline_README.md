# 10-15 ~ 10-22 消费基线说明

> 本文由本人提供事实，AI 协助整理文字。关于佐证的表述已按 2026-11-10 的核查结果更新为「无法提供」，**未做任何替代或重建**。

## 一、数据是什么

本人 2026-10-15 ~ 10-22 的真实消费，共 **39 笔**，日均约 40 元，见 `baseline_2026-10.csv`。
内容真实——每一笔钱都真实花过。

## 二、原始记录载体（关键）

- **载体**：手机备忘录（本人陈述）。
- **方式**：当天花完钱就记一条，写金额和用途（如「3 早餐」「13 午饭」），不是固定时间记，一天可能记三四条，也可能只记一条。
- **结论**：这批记录**是逐日发生的**，只是它一直存在手机里，从未以文件形式进入仓库。
- **重要限制**：上述"逐日记于备忘录"为**本人陈述**；2026-11-10 核查时备忘录条目已无法找到，**无法提供截图或其他佐证**（详见第五节）。因此该陈述**不可被第三方核验**，本文件不据此主张任何过程性结论。

这就是本文件要澄清的核心区别：**记录发生在逐日，但入库方式是一次性的。**

## 三、入库方式（问题所在）

2026-10-22，为了提交阶段二材料，我把备忘录里的 39 笔一次性整理出来，通过 AI 协助写成 `main.js` 中的 `SEED_DATA` 常量，同日导出为 CSV。

- 造成的结果：数据以「源码常量」形式出现在仓库里，读者看到的是「一堆数字」，而不是「一段逐日记录的过程」；
- 行为定性：**入库方式不合规**（事后一次性整理），而非数据内容不真实；
- 已整改：2026-11-09 起 `SEED_DATA` 已从源码移除，数据独立为 CSV；程序改用文件存储，逐笔写入 `data/expenses.json`。

## 四、边界声明

这 39 笔是**消费数据**，不是**程序运行日志**。因此：

- 可作为个人消费基线、可作为需求来源（例如"日均 40 元"这类结论）；
- **不计入**「连续 ≥7 天程序自动化运行日志（Telemetry）」评分项——那一项只能由 2026-11-09 起的真实运行时日志承担。

## 五、独立佐证：无法提供

| 佐证类型 | 状态 | 说明 |
|---|---|---|
| 手机备忘录逐日记录截图 | **无法提供** | 2026-11-10 核查时已无法找到当时的备忘录条目（应用内记录已不存在），未做任何替代或重建 |
| 微信/支付宝账单截图 | **未提供** | 时间跨 8 天、金额分散，暂未逐笔对账 |

**为什么这一格写"无法提供"而不是想办法补一张：**

那份备忘录如果还在，它就是这批数据最硬的证据——带平台时间戳、不来自我的代码、能证明"当时确实逐日记了"。它现在不在了，我能做的只有两件事：

1. 如实写明"无法提供"。这句话本身是可核验的（我确实交不出截图）；
2. 不拿任何其他材料顶替。**如果我为了好看而重建一份"当时的备忘录"，性质就从"记录方式不合规"变成"伪造证据"**——后者是选拔简章里的一票否决项，我不能为了补一个缺口去换一个更严重的问题。

**这对结论有什么影响：**

- 对"数据内容真实"的结论：无影响。39 笔仍是我真实的消费；
- 对"能否被第三方核验"的结论：**有影响**。这批数据现在只能作为**本人陈述 + 个人消费基线**，不能作为独立证据被复核。因此它**更明确地不计入**"运行时日志"评分项，也不用于支撑任何过程性结论。

**因此我改变的做法（见 `REFLECTION.md` 第四节）：**

过去的记录找不回来了，但从 2026-11-09 起，每一笔账都有程序运行时日志、有哈希链、有当日 commit 锚定，任何人可独立复核。**我不打算用解释补过去，用一段改不动的新过程覆盖它。**

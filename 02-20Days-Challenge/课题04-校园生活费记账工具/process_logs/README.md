# process_logs 目录说明（先读这一页）

这个目录里**有两类文件，性质完全不同**。混在一起看会误判，所以单独写一页。

---

## 一、哪类算证据，哪类不算

| 文件名 | 是什么 | 算不算过程证据 |
|---|---|---|
| `telemetry_2026-11-09.log` 起的 13 个 | **程序运行时逐条追加**，每行带前一条的 SHA-256 | ✅ **算。本目录唯一的过程证据** |
| `log_2026-10-15.json` ~ `log_2026-10-22.json`（8 个） | 2026-10-22 由 `main.js` 里的 `SEED_LOGS` 常量经 `writeFileSync` 写出来的 | ❌ **不算。是伪造的运行痕迹**，见仓库根 `CORRECTION.md` 第 1 项 |

**为什么那 8 个不删：** 删掉就等于把问题从仓库里抹掉，读者只能看到「一份干净的日志」和一个空白的时间段。留着、标清楚，比删掉更能说明发生过什么。它们**不参与任何结论，也不计入「连续天数」**。

---

## 二、真日志怎么验

```bash
node src/verify_chain.js
```

- 输出 `[PASS]` + 最终链头，说明 160 条记录前后相接、无篡改；
- 任意改一行：该行 hash 不匹配 + 其后所有 `prev_hash` 断裂，退出码 1。

链的结构：每行 `prev_hash` = 上一行的 `hash`；第一条 `prev_hash` = `GENESIS`。**每个用户的测试副本都是独立的一条链**（各自从 `GENESIS` 起），这一点在 `../../feedback_raw/` 的每份遥测里都能看到。

---

## 三、连续天数怎么核对

见 `连续性核验_2026-11-22.md`：逐日列出遥测行数、`seq` 区间、当日首个运行时刻、当日 git 提交数。

**结论提前说：11-09 ~ 11-19 连续 11 天，日志与提交双满足；11-20 断档，零日志零账目零提交。**

## 五、这些日志能证明什么、不能证明什么

| 能 | 不能 |
|---|---|
| 程序在什么时刻被启动过（毫秒级） | 录入的金额是不是真实花费 |
| 每次录入的金额、分类、耗时 | 用户有没有在程序外思考很久 |
| 出现过哪些报错、被拒绝的输入 | 账本内容本身——`data/` 不进仓库（`.gitignore`） |
| 两个动作之间隔了多久 | 「他为什么这么做」——那要靠记录卡与本人原话 |

这一栏是主动写的：**遥测证明的是「什么时候发生了什么操作」，不是「账是真的」。** 这个边界写在这里，不必由读的人自己去发现。
